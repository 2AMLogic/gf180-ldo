Re-running this SAME testbench topology against the CURRENT (post-#39/#44) ldo_core.spice with a cold, all-zero-guess Newton-Raphson start does not reproduce those sane numbers: #40's investigation found non-physical line-regulation numbers at most PVT points -- root-caused in #40 and fixed here. The deck's ideal current sink had a second, unphysical DC solution in which the pass device is off and the sink holds VOUT tens of volts BELOW ground, drawing its current through forward-biased substrate junctions in the PDK device models; a cold Newton-Raphson start reached that solution at most corners, and #40 showed a .nodeset hint alone could not clear it for a swept deck. The sink is now compliance-limited (see tb_line_reg.spice and sim/harness/README.md, 'Compliance-limited load sinks'): it draws its commanded current for VOUT well above ground and nothing at or below ground, which is what any real load does, and which deletes the unphysical solution rather than biasing the solver away from it. The sink is an ideal current sink to within 1.4e-14 relative error at every operating point reported here, and iload_err_max_ua below measures the worst deviation of the delivered current from the commanded current over all four swept points, so that claim is checked at every corner instead of assumed. No ratified threshold was changed. No device was added, removed or resized, so this is an electrical no-op by construction: an ideal vsource is an ideal vsource wherever it is declared, its return was already the cell's VSS port, and it is an AC short to ground in both placements. It is not asserted on that argument alone -- origin/main at ec9e530 was extracted to a scratch tree and this bench was run on BOTH trees back to back, on the same host with the same ngspice and the same pinned PDK, and the per-corner measurement lines compared field by field; DR-0021's 'Evidence' section tabulates the result.
