- **Claim**: README.md Target specification, 'PSRR' row (DR-0004 amendment A7): >50dB @ 1kHz and >20dB @ 100kHz, C_eff=1uF nominal -- evaluated here at the 50 mA FULL-LOAD condition. This is the load condition sim/psrr-vs-freq/ disclosed as an open gap: that deck is scoped to the 1 mA light-load point (the binding one per README.md note 1) and its tb_psrr.spice header records why the two load points cannot share one deck -- ngspice's per-.meas result vectors go out of scope as soon as a later analysis becomes the current plot, so an 'alter'-and-re-.ac deck silently re-reports the first .ac's numbers. This slug closes that gap the way sim/dropout-vs-load/ already handles its own fixed full-load point: a sibling experiment with the same DUT, the same stimulus and output network, the same full PVT sweep, and its own record carrying its own separate verdict. The two verdicts are deliberately NOT merged -- read this record for the 50 mA condition and sim/psrr-vs-freq/'s record for the 1 mA condition. The load sink is the compliance-limited sink #46 introduced (Vilc/Bload/Vlmeas): it draws its commanded current for VOUT well above ground and nothing at or below it, which deletes the unphysical sub-ground DC solution #40 found rather than biasing the solver away from it. That solution is the dominant risk at this load -- a larger demanded current biases the unphysical root harder -- so dc_vout_v and dc_iload_ma below read the .op plot and are gated at every corner: a PSRR number is only admissible as evidence if the operating point it was linearized about is the physical one and the sink really delivered 50 mA. No ratified threshold was changed by this experiment. Update (#174, 2026-09-05, spec/decision-records/DR-0021): ldo_core's VREF was promoted from an internal net -- driven by Vref1, an ideal 1.2 V vsource instantiated INSIDE the subcircuit -- to a seventh top-level port, and the identical ideal source moved into this deck. No device was added, removed or resized, so this is an electrical no-op by construction: an ideal vsource is an ideal vsource wherever it is declared, its return was already the cell's VSS port, and it is an AC short to ground in both placements. It is not asserted on that argument alone -- origin/main at ec9e530 was extracted to a scratch tree and this bench was run on BOTH trees back to back, on the same host with the same ngspice and the same pinned PDK, and the per-corner measurement lines compared field by field; DR-0021's 'Evidence' section tabulates the result.
