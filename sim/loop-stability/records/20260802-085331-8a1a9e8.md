    Read them side by side:

    | | baseline | head |
    |---|---|---|
    | DC loop gain | 148.105 dB | 148.105 dB (identical) |
    | first falling 0 dB crossing `f0` | 259 304 Hz | 963 296 Hz |
    | phase margin there | 130.54 deg | -65.70 deg |
    | **rising 0 dB crossing above `f0`** | **346 917 Hz** | **none** |
    | gain resurgence above `f0` | not measured (metric did not exist) | -4.07 dB (none) |
    | -180 deg crossing | none found | 782 438 Hz, gain there +22.10 dB |

    The baseline row has a **rising** 0 dB crossing at 346.9 kHz above its
    reported crossover at 259.3 kHz: `|T|` fell through unity at 259.3 kHz
    and climbed back through it at 346.9 kHz. `sweep.py` reports the phase
    margin at the *first falling* crossing, so the baseline's 130.54 deg is
    the margin at a crossing the loop passes through and then comes back
    above -- the loop's final crossing was above 346.9 kHz and its margin was
    never reported. This is exactly the mis-reading
    `spec/decision-records/DR-0008-loop-gain-rhp-pole-precondition.md`
    documents, and the `resurgence_db` column added by #61 exists to catch
    it.

    In the head record that point has **no** rising crossing at all
    (`f0_rising_hz` empty, `resurgence_db` = -4.07 dB), so 963.3 kHz is the
    loop's *final* 0 dB crossing and -65.70 deg / -22.10 dB are the margins
    there. The engineering answer for this point is therefore: **the two
    records are not reporting the same crossing.** The baseline reported the
    first of at least two; the head record reports the only one. The 3.7x
    "crossover shift" is the distance between those two crossings, not a 3.7x
    change in the loop's bandwidth -- the DC loop gain is bit-identical
    (148.105 dB) and `VOUT` is bit-identical (1.7994 V) at this point.

    What this record does **not** claim: that the loop at this point is fine.
    It is not. -65.70 deg PM with `|T|` = +22.10 dB at the -180 deg crossing
    is a bad reading, and the honest summary is that the baseline's `PASS`
    here was never a measurement of this loop's true margin. The point was
    failing before and is failing now; only the number changed.

- **What the 57 are, and are not, evidence of**

  1. They **are** evidence that the DR-0001 pass count fell from 2689 to
     2632 between these two netlists. Issue #55's "no regression" criterion
     is not met and this record marks it not met.
  2. They are **not** evidence that this PR's `BG` port and the two 10 um /
     0.5 um clamp PFETs made the loop less stable, because at 56 of the 57
     the loop-gain curve barely moved (`gm-only`: abs(dPM) <= 0.47 deg,
     crossover <= 5.0%; `pm-wrap-360`: unwrapped residual <= 6.47 deg) while
     the *extraction* changed category -- from "no -180 deg crossing found"
     to "crossing found". A change of that size in the curve cannot create a
     -180 deg crossing below crossover where there was none.
  3. The **hypothesis most consistent with the data** -- stated as a
     hypothesis, not as a measurement -- is the one issue #58 already
     describes. `tph` is `180*cph(t)/pi`; `cph()` unwraps phase by
     accumulating differences between *adjacent grid points*, and at
     `dec 50` a high-Q pole pair at 0.5-0.9 MHz (the feature #53 and #58
     characterise at these exact corners) can advance the true phase by more
     than 180 deg between adjacent samples. When it does, `cph()` picks the
     wrong branch and the whole tail of the phase curve is offset by a full
     turn; `meas ... when tph=-180 fall=1` is a literal test on that vector,
     so a tail sitting one turn high never takes the value -180 and the
     measurement returns empty -> `GM = inf` -> an unconditional pass. A
     capacitance small enough to move the resonance by a fraction of a grid
     step is enough to flip which side of that threshold a point lands on,
     which is why the flips cluster at four cold/high-line corners and at
     0.1-1 mA rather than scattering.
  4. **What would settle it** is a fine-grid (`dec >= 600`) re-probe of the
     57 points on both netlists, which is what #58 asks for as a class and
     what #53 did for 20 points. That probe is **not** run here: this record
     is a comparison of committed evidence, and running it is a separate
     piece of work against #58, not a fix for issue #55.
  5. Consequently, **no number in either record is relaxed and no spec is
     touched.** DR-0001's bars are unchanged, `20260802-071154-166834d`
     still reports `FAIL` overall, and the load-bearing evidence for issue
     #55's actual fix is the time-domain benches (`sim/soft-start/`,
     `sim/startup/`, `sim/current-limit/`, `sim/enable-shutdown/`), not this
     matrix.
