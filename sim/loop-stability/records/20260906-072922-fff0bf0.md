  - **Diagnostic reproduction: the movement is present even with ZERO
    netlist change, so it is not caused by the VREF promotion.** The
    largest single mover above, `ff_125c_2.97v` / 1mA / 0.33uF / 0.2ohm, was
    re-simulated **against the unmodified pre-#174 (six-port) netlist**,
    checked out fresh at `64249c6` into a scratch worktree, run under
    **today's identical toolchain** (same PDK -- `gf180mcuD @
    c6d73a35f524070e85faff4a6a9eef49553ebc2b`, byte-identical hash to the
    baseline record's own stated PDK; same `ngspice-46` binary):

    ```
    git worktree add --detach /tmp/baseline-repro 64249c6
    cd /tmp/baseline-repro
    python3 sim/loop-stability/testbench/sweep.py --corners ff --temps 125 \
      --subset-reason "diagnostic repro for issue #176" -j 3
    #  ff_125c_2.97v   worst PM 4.08 deg  GM 55.24 dB  at 0mA_4.7uF_1mohm   (matches 64249c6 exactly)
    python3 sim/loop-stability/testbench/sweep.py --corners ff --temps 125 \
      --loads-ma 1 --caps-uf 0.33 --esrs 0.2 --no-write -j 1
    #  ff_125c_2.97v   worst PM 60.84 deg  GM 18.41 dB  at 1mA_0.33uF_200mohm
    ```

    The corner-worst value (4.08 deg, the matrix's own overall-worst-adjacent
    point at 0mA/4.7uF/1mohm) reproduces the baseline **exactly**. But the
    *specific* mover point, re-run today on the **unmodified six-port
    netlist against which the original 58.89 deg was recorded on 2026-08-07**,
    reads **60.84 deg -- not 58.89 deg.** That is the identical value (to the
    reported precision) that the post-#174 seven-port netlist produces for
    the same point. Repeating the isolated single-point run reproduces
    60.84 deg deterministically (checked twice); the discrepancy is therefore
    not run-to-run noise *within* today's environment, only a **discrepancy
    between today's environment and 2026-08-07's environment**, on a netlist
    that did not change between those two dates.

    **Conclusion: the ~1-2 deg / ~1 dB movement, and all 5 verdict flips,
    predate and are independent of #174 / DR-0021.** They are a
    pre-existing simulation reproducibility characteristic of this bench at
    its most marginal points (all within ~2 deg of the 45 deg bar), most
    likely floating-point non-associativity somewhere in ngspice's KLU
    factorization or device-model evaluation path across two invocations
    separated by a month of host/library state, though the two runs report
    matching `ngspice-46` version strings and byte-identical PDK model hashes
    and this record does not claim to have isolated which. **Root-causing
    the exact source is out of scope for issue #176**, which asked whether
    the VREF promotion regressed this bench -- it did not -- and is filed
    separately (see Links).

  - **The worst-margin point issue #176 asked to be specifically re-checked
    is reproduced exactly, unchanged:** `tt_27c_3.30v` / 50mA / 0.33uF /
    0.001 ohm (1 mOhm) -- **PM 5.12 deg, GM 1.05 dB** in both
    `64249c6` and `fff0bf0`, bit-for-bit identical to the digits already
    reported in the 72-point `--explore` spot-check issue #174 / PR #179 ran.
    This is also the matrix's global worst point in the "By ESR = 1 mOhm,
    process = tt" slice and sits nowhere near the marginal population the
    5 flips above come from (5.12 deg vs. a ~44-46 deg bar-adjacent
    population).

  - **What this record does NOT claim**: that DR-0021's electrical-inertness
    argument is wrong. It is not -- an ideal voltage source is provably an AC
    short to ground wherever it is instantiated, and the diagnostic
    reproduction above is exactly the control experiment that isolates the
    variable: it holds the netlist fixed (unmodified six-port, `VREF`
    internal, same value as ever) and still reproduces the "moved" number.
    If the promotion itself were the cause, the unmodified netlist could not
    reproduce the head record's value. It does.
