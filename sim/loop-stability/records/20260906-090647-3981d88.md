# Record 20260906-090647-3981d88

- **Record ID**: 20260906-090647-3981d88
- **Claim**: issue #182's acceptance criteria -- root-cause the ~1-2 deg
  phase-margin / ~1 dB gain-margin cross-invocation drift that
  `sim/loop-stability/records/20260906-072922-fff0bf0.md` found and left
  unresolved, with evidence ruling out the alternative candidate hypotheses
  listed in #182's body, and record a remediation decision. This record
  makes no new stability claim: the DR-0001 verdict for the current netlist
  is unchanged (still **FAIL**, tracked by #42), and it does not alter or
  supersede any prior record's own PASS/FAIL verdict.
- **Netlist provenance**: **diagnostic** -- no new full-matrix simulation.
  This record's evidence is (a) a fresh set of single-point re-simulations of
  the exact control point `20260906-072922-fff0bf0.md` already isolated
  (`ff_125c_2.97v` / 1mA / 0.33uF / 0.2ohm), run against the unmodified,
  clean, pre-#174 six-port netlist checked out fresh at `64249c6` into a
  disposable scratch worktree (`git worktree add --detach <tmp> 64249c6`,
  removed after use -- not a persistent issue worktree), and (b) direct
  filesystem inspection of the local ngspice install(s) and gf180mcu PDK
  cache on the host that produced this record. None of this is itself a new
  DUT-netlist simulation result, so nothing here supersedes or is compared
  against any prior record's own verdict.
- **Operating conditions**: the single control point `20260906-072922-fff0bf0.md`
  already isolated as the largest single mover -- `ff_125c_2.97v` corner,
  I_load = 1mA, C_eff = 0.33uF, ESR = 0.2 ohm, enabled steady state, ideal DC
  current load (same convention as every other loop-stability record).

- **Result**:

  This record's own re-simulations, run **today**, on **this host**
  (`robb-studio`, an Apple Silicon Mac, arm64), against the identical netlist
  and PDK content as both prior comparisons, reproduce **58.89 deg / 18.92 dB**
  -- the *original*, pre-drift `20260807-103351-64249c6` baseline value, **not**
  the 60.84 deg / 18.41 dB value `20260906-072922-fff0bf0.md` reported for the
  identical command on the identical day. This is itself informative: it
  means the drift is not a simple "environment moved once, from state A on
  2026-08-07 to state B from 2026-09-06 onward" story -- state A (58.89 deg)
  is still directly reproducible today, on a different host, alongside state
  B (60.84 deg, reported by `fff0bf0`'s own diagnostic on 2026-09-06). Two
  different, both-real values for the identical command, same day, same
  stated toolchain version and PDK hash. The rest of this record narrows down
  why.

  **1. Within-process, within-host determinism holds -- ruling out simple
  per-invocation floating-point noise as the dominant mechanism (issue
  candidate hypothesis (a), narrowly read).** The diagnostic command was run
  28 times in a row on this host, in a fresh scratch worktree at `64249c6`:

  ```
  git worktree add --detach /tmp/issue182-repro-new 64249c6
  cd /tmp/issue182-repro-new
  python3 sim/loop-stability/testbench/sweep.py --corners ff --temps 125 \
    --loads-ma 1 --caps-uf 0.33 --esrs 0.2 --no-write -j 1
  #  ff_125c_2.97v   worst PM 58.89 deg  GM 18.92 dB  at 1mA_0.33uF_200mohm
  #  (identical on all 28 runs)
  ```

  15 runs used no special environment; 6 more were repeated with
  `VECLIB_MAXIMUM_THREADS=1 OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1` to rule
  out an internally-threaded BLAS/LAPACK call inside ngspice's KLU path
  introducing scheduling-order nondeterminism; a further batch was run while
  8 background `yes > /dev/null` processes saturated every core on this
  18-core-class Apple Silicon host, to rule out CPU contention/thermal
  throttling changing which floating-point code path executes. **Every one
  of the 28 runs reported the identical 58.89 deg / 18.92 dB, to the digit.**
  Thread-count pinning and heavy background load make no difference on this
  host. This is strong ruling-out evidence against "unreported environment
  state such as thread count or CPU load, varying invocation-to-invocation
  on a fixed binary" as the dominant driver -- on this host, with this
  binary, the result is not a coin flip; it is a fixed, repeatable number.

  **2. Two binaries with the identical self-reported `ngspice-46` banner
  coexist on this one host, with different content -- and both give the
  ORIGINAL (58.89 deg), not the moved (60.84 deg), value.** This host has
  two independently-built ngspice-46 installs on `PATH`/nearby it:

  ```
  $ shasum -a 256 ~/.local/bin/ngspice ~/.local/ngspice-46/bin/ngspice
  4f076ec866c69842d3a9e93376ac17b3ae0e1709b4ddb05890e0e6488a900b10  ~/.local/bin/ngspice
  6c5c98a9081b421634a7e80941ec12ed16eed4bb36bad746f8ccf0a58afc8810  ~/.local/ngspice-46/bin/ngspice
  $ ls -la ~/.local/bin/ngspice ~/.local/ngspice-46/bin/ngspice
  -rwxr-xr-x  1 rwalters  staff  4973128 Aug 31 19:11 /Users/rwalters/.local/bin/ngspice
  -rwxr-xr-x  1 rwalters  staff  4972696 Aug 30 14:56 /Users/rwalters/.local/ngspice-46/bin/ngspice
  ```

  Both print the identical `"ngspice-46 ... Compiled with KLU Direct Linear
  Solver"` banner (`ngspice -v`/`ngspice --version`); both have different
  sha256 content hashes and different file sizes; both were built (mtime)
  **after** the 2026-08-07 baseline and **before** today's 2026-09-06
  comparisons. This alone is direct, on-disk proof that "same reported
  version string" does not entail "same binary" in this repo's evidence
  convention -- exactly candidate hypothesis (b) from #182's body ("a PDK or
  ngspice binary update that preserved the reported hash/version string but
  changed underlying content"), independent of anything else in this record.
  But re-running the control point through **both** binaries (by
  temporarily prepending each install's `bin/` to `PATH`) gives **58.89 deg
  on both** -- neither of the two binary builds present on this host
  reproduces the 60.84 deg value `fff0bf0`'s diagnostic reported.

  **3. The PDK model content is unchanged and rules out itself as a cause.**
  The resolved `gf180mcuD` variant both this record and every prior one in
  this comparison cite (`c6d73a35f524070e85faff4a6a9eef49553ebc2b`) is a
  `volare`-fetched, content-addressed-by-commit-hash cache directory. Every
  file under it predates the 2026-08-07 baseline and none has been touched
  since:

  ```
  $ REAL=~/.volare/volare/gf180mcu/versions/c6d73a35f524070e85faff4a6a9eef49553ebc2b/gf180mcuD
  $ stat -f "%Sm %N" "$REAL"
  Jul 29 19:52:08 2026 .../gf180mcuD
  $ find "$REAL" -type f -newermt "2026-08-07" | wc -l
         0
  ```

  This directly rules out "a PDK update that preserved the pinned hash but
  changed underlying content" (the PDK half of candidate hypothesis (b)) --
  the content genuinely has not moved since before the baseline. The
  ngspice-binary half of hypothesis (b) is the one with direct evidence (see
  point 2); the PDK half is cleanly ruled out.

  **4. Candidate hypothesis (c) (Newton-seed history from the
  `foreach`/`alter` sweep style) was already ruled out by `fff0bf0`'s own
  diagnostic** -- its isolated single-point run reproduced the same "moved"
  value as the full 72-point sweep, which this record's own isolated
  single-point re-runs are consistent with (an isolated run is exactly what
  both this record and `fff0bf0` used; the difference between the two is not
  explained by sweep-vs-isolated structure).

  **5. Conclusion: the drift is a toolchain-identity gap, not a per-run
  coin flip on a fixed binary, and not a PDK content change.** Loom's own
  per-issue lease-record mechanism (visible directly on issue #182's own
  comment thread) confirms builder work is dispatched across multiple,
  independently-named hosts (this issue's own claim was leased on
  `host-d9142cf3`; this record was produced on `robb-studio`). Neither this
  repo's evidence records nor its harness code has, until now, captured
  *which* host, or *which exact binary content*, produced a given record --
  only a self-reported version string that this record shows is not a
  reliable proxy for either. The most parsimonious explanation consistent
  with every observation above: `ngspice-46` resolves to a genuinely
  different binary on the host that produced `fff0bf0`'s diagnostic than on
  either binary present on this host, and that host's build measurably
  differs in floating-point behavior at this specific numerically marginal
  operating point (a lightly-loaded, low-crossover-frequency corner, exactly
  the kind of point most sensitive to small differences in DC
  operating-point convergence or device-model rounding). This record cannot
  recover the exact bits of whichever binary authored `fff0bf0`'s
  diagnostic to prove that identification further -- that host's install is
  not preserved anywhere this record can inspect -- but the ruling-out
  evidence above (28/28 identical on this host regardless of threading/load;
  two distinct local binaries both giving the *other* value; PDK content
  provably unchanged; sweep-history already ruled out by `fff0bf0` itself)
  leaves a cross-host (or same-host-over-time, per point 2's direct
  same-machine counterexample) toolchain-identity gap as the only hypothesis
  standing.

  **What this record does NOT claim**: that any specific host's ngspice
  build is "wrong" or defective, or that DR-0001's bar should move. Every
  value observed across this whole investigation (58.89, 60.84 deg) is well
  above 45 deg at this specific point -- this bench's own DR-0001 verdict is
  unaffected either way (this point PASSes DR-0001 under either reading; the
  5 points that flip PASS/FAIL near the 45 deg line, tracked in `fff0bf0`,
  are a separate, already-tracked question this record does not reopen).

- **Remediation decision**:

  1. **Tighten the toolchain pin from a version string to a content
     fingerprint.** `sim/harness/runner.py` gains `ngspice_binary_sha256()`,
     a sha256 of the resolved `ngspice` executable, alongside the existing
     `ngspice_version()`. `sim/harness/report.py`'s `environment()` /
     `build_record()` and `sim/harness/cli.py`'s `run()` / `cmd_check_env()`
     thread it through so every future record produced via the generic
     harness carries both the version string and the binary's content hash.
     `sim/loop-stability/testbench/sweep.py` (the bench this drift was found
     in) does the same in its own hand-composed record and console banner.
     Both now also record the producing **host** (`socket.gethostname()`),
     since point 5 above shows the host, not just the binary, is part of the
     toolchain identity that matters.
  2. **Do not widen or relax the DR-0001 bar.** The observed movement class
     (up to ~2 deg PM / ~1 dB GM at points already within a couple of
     degrees of the bar) is a toolchain-provenance question, not a design
     regression, and is documented as such -- but the bar itself
     (45 deg / 10 dB) is unchanged, and no existing record's own verdict is
     retroactively altered by this finding.
  3. **Document the caveat in `sim/README.md`** (new section
     "Reproducibility caveat: a version string is not a content fingerprint
     (#182)"): a record's Environment section now carries a binary-content
     hash and a host, and a delta between two records near a spec bar should
     be checked against those fields *before* being treated as evidence
     about the design. This is additive to, not a relaxation of, the
     existing append-only/PVT-matrix conventions.
  4. **Not attempted here (follow-up filed instead)**: unifying every Loom
     builder host onto one canonically-built, checksum-verified ngspice
     install (so `ngspice-46` means exactly one binary fleet-wide) is a
     fleet-provisioning change beyond this repo's `sim/` evidence format,
     and beyond what a single Builder issue should absorb without expanding
     scope. See Links for the filed follow-up.
